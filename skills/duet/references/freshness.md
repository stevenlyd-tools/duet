# Check remote state before work

At task start/resume, before working on any existing branch, and again before PR submission, merge or deployment, fetch and compare the relevant remote versions. Do not fetch on every edit. Recheck after a meaningful pause or evidence that collaborators changed the branch. Fetch is a normal read of remote work that updates tracking refs; it is not pull, branch synchronization or permission to rewrite work.

## All hosts, including skill-only use

1. Read project instructions. Identify the main **remote and branch**, the current branch/HEAD and its actual upstream (which may be a different remote/name). Inspect status first. Use declared project configuration or main's upstream; if ambiguous, resolve it instead of guessing. An unpushed new branch is valid; a disappeared configured upstream is not evidence of synchronization.
2. Fetch the relevant main remote and current-branch upstream remote using normal Git with existing access. Check the command result; a network/authentication failure means freshness is unknown. Do not claim an old tracking ref is latest. Do not request extra user confirmation for ordinary authorized reads, or change credentials/permissions to make them work.
3. Record fetched main SHA, current HEAD/upstream SHA, ahead/behind/diverged state and uncommitted work. Inspect main-only product-definition changes since the common ancestor (for Suo, `suo/`), separately from local product edits. Missing remote/main, detached HEAD or no remote must be stated explicitly. No remote is local-only evidence, never a verified remote baseline.
4. Before editing an existing branch, integrate incoming upstream work using project policy and a safe strategy. A clean, strictly behind branch can normally fast-forward; preserve dirty changes, unpublished commits and shared history. Report divergence/conflicts and the exact next step when automatic synchronization would be unsafe. Never stash/reset/delete unrelated work, force-push, or rebase shared history automatically. Main drift alone does not force all old experiments to rebuild immediately; review relevant changes and choose a scoped refresh when needed.
5. Create new independent work from the fetched main SHA. An isolated worktree can use that SHA without moving a local main occupied by another worktree. Before PR/merge/deploy, recheck the exact source/base/target versions and tests under project policy; a successful earlier fetch is not a guarantee that the remote cannot move afterward. Persistent Alpha retains its exact provider-SHA checks and retained-data rules.
6. If main changes Suo authority, inspect/export against the exact updated snapshot and review current Unit definitions and coverage applicability. Reconcile current definitions within authorized scope; Git owns history. Do not fabricate approval or copy an old authority tree over newer main. Inspect candidate differences even after a clean Git merge.

## Optional CLI (0.4.0)

`duet --project PATH freshness` works without coordinator initialization. It fetches refs and reports the above comparisons; it never edits working files, local branches or upstream configuration. Use `--main main --remote origin --remote-main main` to name an explicit target. With coordinator configuration, optional `mainRemote`/`mainRemoteBranch` name that target; version-1 configs remain valid and are not rewritten. `mainRemoteBranch` requires `mainRemote`.

Resolution: main's configured non-local upstream remote/branch; otherwise `origin`, otherwise the sole remote; multiple non-origin remotes without main tracking require an explicit choice. An explicit remote override inherits a tracking branch name only when it is the same tracking remote; otherwise the target branch defaults to `mainBranch`. The current branch's own upstream is checked independently. With no upstream, check its same-name branch on the selected main remote and report `unpublished` if absent; this cannot discover an undeclared publication on another remote. Detached HEAD is reported, not silently assigned a branch. Standalone freshness also works in a feature-only clone without local main, using fetched remote main and reporting the missing local ref. Coordinator initialization retains its existing local-main prerequisite. With neither local nor remote main, inspection fails explicitly.

Each remote is fetched once per check, with a bounded timeout and branch-ref pruning. Repeated checks are safe. `freshness` exits unsuccessfully for incoming/diverged/missing current upstream or failed inspection/fetch. Ahead-only unpublished commits are preserved. Main/Suo drift is reported separately. `--dry-run` does not fetch and cannot establish freshness.

Automatic gates:

- `experiment start`, `harden`, and `alpha compose` fetch and use verified remote main directly. A behind local main need not move. Ahead/diverged local main blocks a new baseline rather than silently dropping its unpublished commits. The current coordinator checkout may be dirty; isolated work does not touch it.
- `experiment resume ID` checks that experiment's branch before continuing and reports main/Suo drift without rewriting its pinned baseline. `checkpoint` and local-source `harden` refuse incoming/diverged/deleted upstream work. Checkpoint still commits the experiment's intended edits; inspect its scope first.
- `harden-check` fetches the hardening branch upstream and main, requires a clean branch containing fetched main, then runs checks. Integrate main by the project's safe merge/rebase policy before retrying. Local-only fixtures retain existing ancestry checks without a remote-freshness claim.
- `alpha check` rechecks the composed main baseline; `reconcile` fetches and verifies the exact integrated commit against remote main. It does not update remaining worktrees. Persistent Alpha's separate provider adapter continues to check its selected branch/SHA; use task-level `freshness` before that route to review main/Suo drift too.
- `status`, `alpha plan`, and `handoff` remain local/read-only and do **not** prove freshness. Their local-main plan may differ from the next fetched composition. No background fetch daemon, automatic pull/rebase, persisted freshness approval or new credentials are introduced.

Managed experiments retain their immutable baselines. To intentionally refresh one, create a new ID on verified main, transfer only outstanding selected work and declared dependencies, test, then replace the old selection. Do not merge main into an old managed baseline and snapshot its entire diff.
